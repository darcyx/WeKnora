# 反馈管理页面设计

状态：待评审设计，尚未实现后台页面或查询接口。

## 目标与入口

在左侧主导航「共享空间」正下方增加同级菜单「反馈管理」，不单独分组。顺序为：新对话 → 知识库 → 智能体 → 共享空间 → 反馈管理，随后是按日期分组的会话历史。建议路由 `/platform/feedback`，面向租户管理员及 Owner。统一查看聊天回答和直接展示的 FAQ 反馈，优先解决“用户不满意什么、当时看到什么、哪条 FAQ 应该修改”。全局管理员也先选择工作空间，默认不做跨租户看板。

界面延续 Vue + TDesign，使用现有颜色、间距和国际化体系。左侧保持后台导航，主区域为统计摘要、筛选器、列表，详情通过右侧 560–640px 抽屉展开。窄屏详情占满可用宽度。交互草图使用示例数据，不表示已有统计结果。

## 首版范围

1. 反馈明细：统一检索 FAQ 和聊天反馈。
2. 详情抽屉：完整反馈原因、问题、回答及定位信息。
3. FAQ 汇总：按条目聚合反馈，识别重复问题。
4. 导出：导出当前筛选结果。

首版不增加处理状态、负责人、评论或批量修改；后台管理员不能修改或删除用户投票。未来如需处理流程，用单独的处理记录，不改写原始反馈。

## 页面与交互

顶部为「反馈管理」和导出入口。默认最近 7 天、全部来源、全部评价，最新反馈优先。三个摘要为反馈数、点踩数、点赞占比；点击点踩数切换点踩筛选。

筛选器：

- 时间范围：最近 7 天 / 30 天 / 自定义，按反馈提交时间筛选。
- 来源：全部 / FAQ / 聊天回答。
- 评价：全部 / 点赞 / 点踩。
- 点踩原因：回答不准确、回答不完整、答非所问、其他，可多选，选中项之间取 OR。选原因时自动选择点踩并明确显示筛选条件。
- 搜索：问题或反馈说明；展开高级筛选可按 session_id、request_id、FAQ ID、用户标识精确查找。
- FAQ 来源下可增加知识库、分类筛选；聊天知识库来源可能多值，首版不强行套用相同筛选语义。

分页默认 20 条，筛选变化回到第一页，条件和页码写入 URL。详情关闭后保留滚动位置与筛选。摘要和列表遵循同一组条件，避免统计与列表不一致。

列表列：反馈时间 / 来源 / 问题摘要 / 评价与原因 / 用户 / 查看。FAQ 的问题摘要下显示知识库与分类；聊天显示会话标题。ID 保留在详情与精确筛选中，不把长 UUID 堆在列表上。空问题使用「问题内容不可用」，不捏造原问题。

空数据、筛选无结果、加载失败分别显示，并提供重置筛选或重试；请求中保持布局稳定。

## 详情抽屉

上部：评价、反馈时间、点踩原因标签、完整补充说明。

FAQ 详情：

- 首先展示 `faq_feedbacks.standard_question` 与完整 `answers`，标注「反馈提交时的 FAQ 内容」。
- 支持查看相似问、反例、回答策略、分类、知识库标识。
- 区分 FAQ 标准问题和用户实际提问。现有表没有保存实际提问，不能把标准问题标成用户原话。
- 「查看当前 FAQ」单独读取当前条目，并区分“当时内容”和“当前内容”。目标已删除时仍展示反馈表中冗余的内容，当前条目入口显示不可用。
- 现有数据是提交反馈时读取的 FAQ 全部答案，不保证等于用户先前实际看到的答案，也不能确定随机策略具体展示了哪一条；界面不作这种承诺。

聊天详情：

- 用 `session_id + request_id` 读取 `role=assistant` 的回答，用同一请求匹配用户问题。
- 展示问题、回答及存在的引用资料；不要把工具调用、推理过程默认全部展开。
- 请求下存在多条助手记录时返回实际带 feedback 的目标记录及真实消息主键，禁止任意选第一条造成反馈与回答错配。
- 消息被修改时，现有数据不能恢复提交时的历史回答，界面只标「消息内容」。已删除内容不能伪造恢复。

底部定位区：来源、当前租户、用户/外部主体、session_id，以及 FAQ entry_id 或 request_id；支持复制。「查看会话」跳转已有会话页面，并以真实消息 ID 定位聊天反馈。API 反馈用户可能是外部用户或 API Key 主体，无法解析姓名时显示实际主体标识。

抽屉通过明确的查看按钮打开，支持 Esc 关闭、键盘焦点管理、上一条/下一条浏览。所有来源内容按现有安全 Markdown 渲染机制处理。

## FAQ 汇总

按当前租户的 entry_id 分组，展示：标准问题 / 知识库及分类 / 反馈数 / 点赞数 / 点踩数 / 点赞占比 / 最近反馈时间。

默认按点踩数降序，随后按最近反馈时间排序。支持按评价数排序。比例同时显示样本量，不能仅按低比例把只有 1 条反馈的 FAQ 排到最前。

点击条目切换到明细并自动带入 FAQ ID，保留时间范围。不同会话的反馈分别计数，符合现有“同会话同 FAQ 只能反馈一次”的规则。

同一 FAQ 的冗余内容可能随提交时间变化。汇总标题使用所选时间段内最新一条反馈保存的标准问题，并标注数据口径；单条详情始终显示该行保存的内容。首版只按稳定 entry_id 聚合，不按问题文本去重，不做版本推断。

## 指标口径

- 反馈数 = 符合筛选条件的反馈记录数，不是用户人数或消息总数。
- 点赞占比 = 点赞数 /（点赞数 + 点踩数），无记录时显示「—」。不能称为整体满意度或准确率。
- 原因分布如后续加入：分母为点踩记录数；一条反馈可多选，比例相加可能超过 100%。
- 当前没有 FAQ 展示次数，首版不提供反馈率。跨会话重复反馈不能去重成一条。
- 时间按 `feedback.created_at` 计算，不使用消息或 FAQ 创建时间；后端用 UTC，前端展示工作空间/用户时区，并明确日期区间为左闭右开。

## 数据与接口建议

保持现有写入结构：聊天来自 `messages.feedback`，FAQ 来自 `faq_feedbacks`，不引入新的统一反馈表。新增查询服务将两类记录映射成统一 DTO。

建议接口（均为新增设计）：

- `GET /api/v1/feedback`：分页明细及同条件摘要。
- `GET /api/v1/feedback/{source}/{session_id}/{target_id}`：单条详情，source 为 faq/message；target_id 分别为 FAQ ID 或 request_id。
- `GET /api/v1/feedback/faq-summary`：FAQ 聚合分页。
- `GET /api/v1/feedback/export`：当前筛选条件下的 CSV；设置数量上限，超过时明确提示缩小范围。首版可采用 10,000 条上限。

静态路径在路由中应与详情模式明确区分。所有参数验证长度、日期范围与允许值。

统一列表字段建议：`source`、`session_id`、`target_id`、`message_id`（聊天真实主键）、`user_id`、`user_label`、`question_excerpt`、`answer_excerpt`、`feedback`、`knowledge_base_id`、`knowledge_base_name`、`tag_name`、`content_available`。前端行键使用 source + session_id + target_id，不按 target_id 单独去重。若同一请求产生多个实际反馈记录，应增加真实 message_id 区分，并同步调整详情寻址。

列表查询在数据库层用同租户约束分别查询两类来源后 `UNION ALL`，统一排序与分页，禁止分别分页后在内存拼接。稳定排序按 feedback.created_at 降序，再按 source/session_id/target_id 等稳定键排序。不做逐行用户或会话查询；批量补充显示名称，详情再取大字段。

统计与分页在同一响应中返回相同过滤条件下的聚合结果。FAQ 聚合直接读取 faq_feedbacks；内容无需回查 chunks。

反馈时间和评价当前在 JSON 内。先测量查询计划；数据规模需要时，为 PostgreSQL 添加按反馈时间的部分/表达式索引，为 SQLite 使用等效表达式索引。不要为了设计页面立即改写反馈存储结构。

## 权限与数据边界

- 后台入口与查询接口统一限制为当前工作空间 Admin+；租户来自认证上下文，不能信任客户端传 tenant_id。
- 管理查看需要明确的后台授权方法，不复用仅允许会话所有者的反馈写入查询方法，也不放宽反馈写入权限。
- 所有详情、聚合、导出均独立校验租户；同名用户、相同 session_id 或 request_id 不能穿透租户边界。
- FAQ 汇总不依赖条目仍存在；聊天反馈随消息软删除后的展示策略需要实现时确定，默认遵守现有软删除范围。
- 导出遵循同一权限和筛选规则，对 CSV 公式字符进行处理。原始文本不执行 HTML/脚本。

## 验收要点

1. 两种来源的投票在统一列表正确展示，FAQ 数字 ID 不会被当成消息主键。
2. 支持查看 FAQ 冗余问题、全部答案和原因；当前 FAQ 修改不影响历史反馈内容。
3. 相同 FAQ 的不同会话分别展示；相同 request_id 在不同会话或租户间不串数据。
4. 过滤后摘要、列表、导出同口径；分页跨来源没有遗漏与重复。
5. FAQ 汇总数量与明细吻合，无样本比例显示「—」。
6. 非管理员不能读取后台接口，跨租户查询无数据泄露。
7. 不出现无数据支持的处理状态、准确率或用户实际展示答案。
